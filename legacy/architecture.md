# Architecture — Finance Lab Client Delivery Management System (V1)

## 1. Purpose and platform

A Client Delivery Operations System built on Google Sheets (data + UI) and Google Apps Script (logic + automation). No VBA. The codebase is deliberately modular and layered so that V1's business logic can later be lifted into a real backend for a web application (see `docs/future-architecture.md`), without rewriting the rules themselves.

## 2. Core entities

| Entity | Sheet | Represents |
|---|---|---|
| Client | `CLIENTS` | A company Finance Lab provides services to. |
| Employee | `EMPLOYEES` | A Finance Lab staff member who can be assigned work. |
| Service | `SERVICES` | One line item in Finance Lab's service catalog (e.g. "Bank Reconciliation"). |
| Service Package | `SERVICE_PACKAGES` | A named bundle of services sold to a client (e.g. "Full Finance"). |
| Task Template | `TASK_TEMPLATES` | A reusable definition of recurring work, scoped to a package + service area + frequency. |
| Task | `TASKS` | A concrete unit of work for one client, one period, generated from a template or created manually. |
| Monthly Period | implicit (`Period` column on `TASKS`, `Month` on `MONTHLY_CLOSE`) | A `YYYY-MM` string identifying which month/period a recurring task or close instance belongs to. Not a standalone sheet — it's a value, not an entity with independent state. |
| Client Request | `CLIENT_REQUESTS` | Something Finance Lab is waiting on the client to provide. |
| Issue | `ISSUES` | A problem or risk affecting delivery for a client. |
| Activity | `ACTIVITY_LOG` | An audit trail entry recording a significant system event. |

Supporting/derived sheets: `MONTHLY_CLOSE` (one row per client per month, tracking close-stage status), `SETTINGS` (system configuration, enum values, thresholds), `CONTROL_CENTER` / `CLIENT_DASHBOARD` / `TEAM_DASHBOARD` / `MONTHLY_CLOSE_DASHBOARD` (read-only rendered views, not sources of truth), `_CHART_SRC` (hidden pivot source for charts).

## 3. Relationships

```
CLIENT (CLIENTS)
  │
  ├── has one SERVICE_PACKAGE (Clients.Service Package → ServicePackages.Package Name)
  │
  ├── has many TASKS (Tasks.Client ID → Clients.Client ID)
  │     └── each TASK optionally originates from a TASK_TEMPLATE
  │           (matched by Template ID at generation time; not stored as an FK on Tasks —
  │            duplicate-detection instead keys on Client ID + Service Area + Task Name + Period)
  │
  ├── has many CLIENT_REQUESTS (ClientRequests.Client ID → Clients.Client ID)
  │
  ├── has many ISSUES (Issues.Client ID → Clients.Client ID)
  │
  ├── has many ACTIVITY_LOG entries (ActivityLog.Client → Clients.Client Name)
  │
  └── has many MONTHLY_CLOSE rows, one per month (MonthlyClose.Client → Clients.Client Name)

EMPLOYEE (EMPLOYEES)
  │
  ├── is Account Manager / Backup Team Member for many CLIENTS
  ├── is Assigned To on many TASKS
  ├── is Assigned To on many CLIENT_REQUESTS / ISSUES
  └── is Default Assignee (by role) on many TASK_TEMPLATES

SERVICE_PACKAGE (SERVICE_PACKAGES)
  │
  └── includes many SERVICES (free-text "Included Service Areas" referencing SERVICES.Service Name)
        └── determines which TASK_TEMPLATES apply (TaskTemplates.Service Package → ServicePackages.Package Name)

TASK_TEMPLATE (TASK_TEMPLATES)
  │
  └── expands into many TASKS (one per client per period the template applies to)
```

Sheets reference each other by **name/ID string match**, not native spreadsheet cell references — this keeps rows independently editable and matches how a future relational backend would model foreign keys (see `docs/future-architecture.md`).

## 4. ID scheme

IDs are short, prefixed, zero-padded, sequential, and generated by `utils/IdLogic.gs` (pure: scans existing IDs for the highest suffix, pads +1) wrapped by `utils/IdService.gs` (reads the relevant sheet's ID column).

| Entity | Format | Example |
|---|---|---|
| Client | `CL-0001` | CL-0007 |
| Employee | `EMP-001` | EMP-012 |
| Task | `TSK-000001` | TSK-004321 |
| Task Template | `TPL-001` | TPL-014 |
| Client Request | `REQ-0001` | REQ-0088 |
| Issue | `ISS-0001` | ISS-0021 |
| Activity | `ACT-0000001` | ACT-0001234 |
| Monthly Close | `MC-<ClientID>-<YYYYMM>` | MC-CL-0007-202608 |
| Service | `SVC-001` | SVC-014 |
| Service Package | `PKG-001` | PKG-003 |

## 5. Statuses and priorities

Canonical values live in `apps-script/config/Enums.gs` and are seeded into `SETTINGS` as named ranges — the sheet dropdowns read from those named ranges (not literal arrays), so most lists are extensible from `SETTINGS` alone. Values that are structurally load-bearing in engine logic (compared with `===` inside pure-logic modules) are marked **[code-significant]** below and documented again in `docs/admin-guide.md` as editable-with-caution: renaming them breaks automation unless the corresponding `Enums.gs` constant is updated too.

- **Task Status**: Not Started, In Progress, Waiting Client, Blocked, In Review, **Completed** [code-significant], **Cancelled** [code-significant].
- **Priority** (Tasks, Requests, Issues where applicable): Low, Medium, High, **Critical** [code-significant — drives weighted completion and health rules].
- **Client Health**: On Track 🟢, At Risk 🟡, Delayed 🔴, **On Hold** ⚪ [code-significant — hard override].
- **Contract Status**: Onboarding, **Active** [code-significant — gates monthly generation], On Hold, Completed, Cancelled.
- **Client Request Status**: Requested, Partially Received, **Received** [code-significant], Not Available, Cancelled.
- **Issue Severity**: Low, Medium, High, **Critical** [code-significant].
- **Issue Status**: Open, In Progress, **Resolved** [code-significant], Cancelled.
- **Review Status**: Not Reviewed, In Review, Approved, Changes Requested.
- **Frequency** (templates/tasks): Daily, Weekly, Monthly, Quarterly, Annually, One-Time.
- **Reporting Frequency** (client-level): Weekly, Monthly, Quarterly.
- **Monthly Close stage status** (used across the 18 stage columns in `MONTHLY_CLOSE`): Not Started, In Progress, **Completed** [code-significant], Blocked, Waiting Client.

## 6. Calculated fields

| Field | Sheet | Mechanism | Rule |
|---|---|---|---|
| Days Remaining | TASKS | live `ARRAYFORMULA` | `Due Date - TODAY()` if task is open (not Completed/Cancelled); blank if no due date or task closed. |
| Days Overdue | TASKS | live `ARRAYFORMULA` | `TODAY() - Due Date` if open, has a due date, and due date has passed; else `0`. |
| Days Waiting | CLIENT_REQUESTS | live `ARRAYFORMULA` | `TODAY() - Requested Date` while outstanding; frozen at `Received Date - Requested Date` once Received/Not Available/Cancelled. |
| Days Waiting Bucket | CLIENT_REQUESTS *(added, see §9)* | live `ARRAYFORMULA` | `0-3` / `4-7` / `8-14` / `15+` from Days Waiting. |
| Simple Completion % | CLIENTS *(added, see §9)* | script-computed (`ProgressEngine`) | `Completed tasks / Total non-cancelled tasks`, per client. |
| Weighted Completion % | CLIENTS *(added, see §9)* | script-computed (`ProgressEngine`) | Same numerator/denominator logic, but each task counts by priority weight (Critical=4, High=3, Medium=2, Low=1) instead of 1. |
| Client Health | CLIENTS | script-computed (`HealthEngine`) | See §7. |
| Monthly Close Completion % | MONTHLY_CLOSE | live formula | `COUNTIF(stage columns,"Completed") / COUNTA(stage columns)`. |
| Monthly Close Status | MONTHLY_CLOSE | live formula | Closed / Blocked / In Progress / Not Started, derived from Completion % and presence of any Blocked stage. |
| Last Activity, Next Deadline | CLIENTS | script-computed, refreshed alongside progress/health | Most recent `ACTIVITY_LOG` timestamp for the client; earliest open `TASKS.Due Date` for the client. |

**Why the split (formula vs. script)**: date arithmetic that must always be correct the instant the sheet is opened (Days Remaining/Overdue/Waiting) is a live formula — no trigger dependency, never stale. Cross-sheet aggregates whose *rules* may evolve (completion weighting, health thresholds, dashboard rollups) are computed once by a script and written as a value, so the rule lives in exactly one place (reusable later in a backend) instead of being duplicated as both a formula and a script.

## 7. Automation logic

- **`createNewClient(fields)`** (`clients/ClientService.gs`): validates required fields → generates Client ID → appends CLIENTS row → generates onboarding tasks from the client's Service Package templates (`tasks/TaskGenerationOnboarding.gs`, itself built on the shared `templates/TemplateExpansionLogic.gs`) → logs one "Client Created" activity → triggers an initial progress/health recalculation. Duplicate clients (same Client Name + Company Name) are rejected.
- **`generateMonthlyTasks(period?)`** (`tasks/TaskGenerationMonthly.gs`): for every client with Contract Status = Active, expands each applicable active template (frequency must "hit" the target period) into a task, skipping any (Client, Service Area, Task Name, Period) combination that already exists — so re-running never duplicates and never touches prior months' tasks. Logs one summary activity entry per run.
- **Progress engine** (`tasks/ProgressEngine.gs`): recalculates Simple and Weighted Completion % for a client (or all clients) from that client's current TASKS rows.
- **Health engine** (`clients/HealthEngine.gs`): recalculates Client Health from current task/issue statistics and SETTINGS-defined thresholds. Rule set:
  1. Contract Status = On Hold → **On Hold ⚪** (checked first, overrides everything else).
  2. Any Critical-priority overdue task, OR overdue task count ≥ `HEALTH_DELAYED_OVERDUE_COUNT`, OR any open Critical issue → **Delayed 🔴**.
  3. Overdue task count ≥ `HEALTH_AT_RISK_OVERDUE_COUNT`, OR a Critical/High-priority task is due within `HEALTH_AT_RISK_DUE_SOON_DAYS` days, OR any open High issue → **At Risk 🟡**. (Deliberately scoped to Critical/High priority tasks only — otherwise any client with routine recurring work due this week would be permanently "At Risk", which isn't a meaningful signal.)
  4. Otherwise → **On Track 🟢**.
  Thresholds are SETTINGS values, editable without a code change.
- **Client Request automation** (`requests/ClientRequestLogic.gs`): buckets outstanding requests by Days Waiting and flags 15+ day requests as needing attention; surfaces top clients by outstanding-request count.
- **Issue surfacing** (`issues/IssueLogic.gs`): identifies Critical/High and overdue/unresolved issues for the Control Center.
- **Activity logging** (`automation/ActivityLogger.gs`): appends one row per significant event (task created/completed/reassigned, status changed, client added, request created, issue created/resolved, monthly generation run). Pure recalculation writes (formula refreshes, per-open dashboard renders) are never logged.
- **Triggers** (`automation/Triggers.gs`): `onOpen` builds the navigation menu; an installable `onEdit` handles status-change logging/recalculation and Client Dashboard re-render on dropdown change; time-driven triggers run daily recalculation and monthly task generation.

## 8. Layering: pure logic vs. Sheets I/O

Every engine is split into two files:

- **`*Logic.gs`** — pure functions. Take and return plain JS values/objects. Never call `SpreadsheetApp`, `Session`, `Utilities`, or any other Apps Script global. Examples: `DateLogic.gs`, `ProgressLogic.gs`, `HealthLogic.gs`, `TaskLogic.gs`, `IdLogic.gs`, `ClientRequestLogic.gs`, `IssueLogic.gs`, `WorkloadLogic.gs`, `TemplateExpansionLogic.gs`, `ManagementReportLogic.gs`.
- **`*Service.gs` / `*Engine.gs`** — I/O wrappers. Read rows from the relevant sheet(s), call the pure function, write results back, call `ActivityLogger` where appropriate.

This split exists for two reasons: it's what makes any part of the business logic testable outside of Apps Script (see `tests/`), and it's the exact seam that a future backend (Phase 23 / `docs/future-architecture.md`) will lift out — the `*Logic.gs` files can move into a Node/Python service almost unchanged, while only the I/O wrappers get rewritten against a real database instead of Sheets.

## 9. Confirmed deviations from the literal spec

1. **CLIENTS**: the spec lists a single `Overall Progress` column, but Phase 8 requires both Simple and Weighted Completion % to be *displayed*. Resolved by using two columns, `Simple Completion %` and `Weighted Completion %`, in place of `Overall Progress`.
2. **CLIENT_REQUESTS**: the spec's column list has no persisted bucket field, but Phase 14 requires bucketing (0-3/4-7/8-14/15+) and flagging 15+ requests. Resolved by adding a formula-driven, protected `Days Waiting Bucket` column so dashboards can `COUNTIF` it directly and the raw sheet is sortable by bucket.

Both were confirmed with the project stakeholder before implementation.

## 10. Security and configuration separation (Phase 21)

- No API keys, tokens, or credentials are required for V1 — it runs entirely under the container-bound Apps Script project's own authorization (Sheets/Drive scopes granted once at setup).
- Any future external integration (see `docs/future-architecture.md`) that needs a secret must store it in `PropertiesService` (Script Properties), never as a literal in source or a sheet cell.
- Config (sheet names, column layouts, enum values, thresholds) is fully separated from business logic: everything lives in `apps-script/config/`, and every other module reads through it rather than embedding literals.
- Computed columns (Days Remaining/Overdue/Waiting, Client Health, Completion %) are sheet-protected so only the script's execution identity (or explicitly named editors) can write them; the `ACTIVITY_LOG` sheet is similarly protected as an append-only audit trail.
- Least-privilege note for V1: only the spreadsheet owner and explicitly added editors should have Edit access to `CONTROL_CENTER` and `SETTINGS`; broader staff access should be Viewer/Commenter unless they need to update task status, in which case share only `TASKS`/`CLIENT_REQUESTS`/`ISSUES` edit rights. Full role-based access control is deferred to the future web application (see `docs/future-architecture.md`).

## 11. Row-range convention

All `ARRAYFORMULA`/`QUERY` ranges use a fixed constant, `MAX_DATA_ROWS = 2000` (defined in `apps-script/config/Constants.gs`), instead of full-column references — keeping formulas predictable and performant. If a sheet grows past this, `MAX_DATA_ROWS` is raised in one place and `setupSpreadsheet()` re-run.
